## 0) ملخّص تنفيذي

مشروعهم **أوسع نطاقًا (scope)**: يضيف نظام دعم العملاء، نقاط الولاء، مدفوعات Stripe حقيقية، Redis،
إشعارات بريد، واسترجاع كلمة المرور — مع **suite اختبارات jest فعلية** وأنماط تصميم (State/Chain).
مشروعنا **أنظف هندسيًا وأقوى في طبقة الأنواع والتوثيق** (OpenAPI من Zod، فصل توكنات، حساب Decimal)
لكنه **أصغر وظيفيًا**. أهم ما ينقصنا فعليًا: **استرجاع كلمة المرور، اختبارات، Helmet، بوّابة دفع حقيقية،
وRBAC متعدّد الأدوار**.

## 1) أمان وتقوية (Security / Hardening) — أولوية عالية

| الفجوة                       | لديهم                                                    | لدينا                | الحالة                                                                           |
| ---------------------------- | -------------------------------------------------------- | -------------------- | -------------------------------------------------------------------------------- |
| **Helmet (رؤوس أمان + CSP)** | `app.use(helmet())` + CSP مخصّص                          | لا شيء               | ✅ منفّذ لديهم — **ننقصه**                                                       |
| **استرجاع كلمة المرور**      | forgot / reset-from-link / change-password (عميل + لوحة) | غير موجود (مؤجَّل)   | ✅ منفّذ لديهم — **ننقصه**                                                       |
| **Rate limiting**            | مجلد `rate_limiting/`                                    | لا شيء               | 🟡 **عندهم ملف فارغ (stub)** — كلانا فعليًا بلا تطبيق                            |
| **إبطال refresh صريح**       | `DELETE /refresh-token`                                  | إبطال عند logout فقط | ✅ لديهم endpoint مستقل (لكن لدينا الآن تخزين hash للـ refresh وهو أقوى at-rest) |

**ملاحظة لصالحنا:** نحن نفصل توكنات access/refresh عبر claim نوع، ونلزم `CORS_ORIGIN`/`JWT_REFRESH_SECRET`
في الإنتاج، ونخزّن hash للـ refresh — وهي نقاط أمان قد لا تكون لديهم. الفجوة الحقيقية: **Helmet + استرجاع كلمة المرور**.

## 7) خطة سدّ الفجوات حسب الأولوية

**المجموعة أ — سريعة وعالية القيمة (نوصي بها فورًا):**

1. **Helmet** (سطر واحد + CSP) — تقوية فورية.
2. **استرجاع كلمة المرور** (forgot/reset/change) — ميزة أساسية ناقصة فعلًا لدينا.
3. **إعادة suite اختبارات** (Vitest/Jest + supertest) لتدفقات auth/cart/order — أهم فجوة جودة.

**المجموعة ب — ميزات مجال متوسطة:** 4. **RBAC متعدّد الأدوار** (توسيع enum أو جدول أدوار + `requireRole`). 5. **بوّابة دفع حقيقية (Stripe)** + webhook — إن كان مطلوبًا في المواصفات. 6. **إشعارات بريد (nodemailer)** — يخدم #2 (روابط إعادة التعيين) وإشعارات الطلب.

**المجموعة ج — بنية تحتية/تحجيم (عند الحاجة):** 7. **Redis** للسلة/التخزين المؤقت + **retry** على الاتصالات الخارجية. 8. **Rate limiting** فعلي (لاحظ أنه stub فارغ لديهم — فرصة لنتفوّق).

**المجموعة د — توسّعات اختيارية:** 9. نظام **تذاكر دعم**، **نقاط ولاء**، **تقييم مطاعم**، **أرشفة سلة** — حسب نطاق المشروع المطلوب.

## 8) النقاط الموجودة عندهم وغير موجودة عندنا — مرتّبة

```
1.  استرجاع كلمة المرور (forgot / reset / change password)
2.  Helmet (رؤوس أمان + CSP)
3.  Test suite فعلية (jest + supertest)
4.  RBAC متعدّد الأدوار (SUPER_ADMIN/ADMIN + requireRole)
5.  بوّابة دفع حقيقية (Stripe) + webhooks
6.  إشعارات بريد (nodemailer)
7.  Redis (تخزين مؤقت للسلة + health)
8.  آلية Retry للاتصالات الخارجية
9.  وحدة دعم العملاء / تذاكر (SupportTicket)
10. نقاط الولاء (Loyalty Points)
11. إبطال refresh صريح (DELETE /refresh-token)
12. ملخّص الطلب + تتبّع مُفصّل (OrderSummary / OrderTracking كوحدات)
13. تقييم المطاعم (RestaurantRate)
14. أرشفة السلة (CartArchive)
15. تهيئة بوّابات الدفع (PaymentConfiguration / PaymentIntegrationType)
16. State Pattern لحالات الطلب
17. Chain of Responsibility لإنشاء الطلب
```

### النقاط التي لا غنى عنها ولا يجوز تجاوزها (الحدّ الأدنى)

```
1. استرجاع كلمة المرور (forgot / reset / change)   ← نقص وظيفي أساسي في أي auth حقيقي
2. إشعارات بريد (nodemailer)                        ← شرط لتسليم رابط إعادة التعيين (تابع لـ #1)
3. Test suite فعلية                                 ← بلا اختبارات المشروع غير مكتمل مهنيًا/أكاديميًا
4. Helmet (رؤوس أمان)                               ← تقوية أساسية، تكلفتها سطر واحد
```

> RBAC متعدّد الأدوار يصبح «لا غنى عنه» فقط إذا تطلّبت المواصفات أدوارًا غير CUSTOMER/ADMIN.
> باقي النقاط توسّعات نطاق، تجاوزها جائز إن لم تطلبها المواصفات.

## 9) تنبيهات أمانة (لا تطارد الوهم)

- **Rate limiting لديهم = ملف فارغ** (`rate-limit.ts` بصفر أسطر) — ليس ميزة فعلية.
- **`RestaurantRate` / `CartArchive` / `PaymentConfiguration` = نماذج schema بلا endpoints** على الفرع المفحوص — فجوات نظرية لا وظيفية.
- وحدة **المطعم لديهم** = repository/service فقط (بلا routes ظاهرة) — تصفّح الكتالوج لدينا أكمل من هذه الناحية.
- ميزاتهم موزّعة على عدّة فروع؛ قِيس التقرير على فرع `feature/user-management` (الأكثر دمجًا). قد تختلف التفاصيل قليلًا بين فروعهم.
